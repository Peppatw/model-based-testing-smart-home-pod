Slide 00

Why Model-Based Testing?

Where regression testing stops

  • Written step by step, in that order. The library first, then a case against it for each thing worth checking, then the automation — which lands after the feature has shipped.
  • Every case asserts something a person already suspected. So the suite grows with author time and covers what somebody thought of; what nobody thought of stays uncovered, release after release.

What model-based testing is

  • You write down the device, not the cases. Its states, the actions that move between them, and what must be true before each call and after it.
  • The runs are generated from that model. Cases become an output rather than an input — adding a test means adding to the model, and every run afterwards can use it.

What a Markov chain is

A Markov chain is a mathematical system that shifts from one state to another based on fixed probabilities, where the next state depends only on the current state and not on the past. [1]

How It Works

  • States: The distinct conditions or situations a system can be in (like sunny or rainy weather).
  • Transitions: The movement from one state to another.
  • Markov Property: The rule that the future depends entirely on the present moment, making the process "memoryless".
  • Transition Matrix: A square table showing the mathematical odds of moving from any specific current state to any other future state. [1] [2] [3] [4]

Traditional Regression vs AI-Driven MBT

DimensionScripted regressionAI-Driven MBT

One walk that keeps going and carries its own history; a device that has recovered from failure fifty times is the ordinary condition.
Fault timingStatic. Injected at a step somebody chose — usually a step the code already expects it at.Mid-flight. An independent clock cuts in while a call is still in progress.
Who writes itEvery case. Coverage grows with author time, and the automation arrives after the feature ships.The model, once. Runs are generated from it, so coverage grows with machine time — and it can start the day the API library exists.
When it failsThe case is the reproduction.The run is recorded as a schedule — worker, action, offset — so a random finding comes back replayable. Random testing without that record is what gives random testing its bad name.
What it provesThe known. The bug we fixed last release is still fixed.The unknown. The design flaw nobody thought to write a case for.
  • Two ways to walk the same model. State-led follows the chain — realistic paths, which is what a fault needs to be perturbing something worth perturbing. Action-led ignores the chain and fires at whatever state it finds, which is the only way to reach the calls the model says should never happen.
  • And the AI never rolls the dice. It turns an engineer's intent into the plan — which components walk, how long, which faults fire when — then reads the finished run. During the run there is none: dice, guards, oracle and coverage are ordinary Python, reproducible from a seed.
  • Nothing here replaces the existing suite. The scripted paths keep running exactly as they do now, on the same bench.

What running it looks like

t+00:00  wifi    connect_wifi                   Disconnected -> Connected
t+00:02  bt      bt_pairing                     Unpaired -> Pairing
t+00:05  matter  start_matter                   Uncommissioned -> Commissioning   (guard: wifi=Connected OK)
t+00:09  wifi    streaming_uplink               Connected -> Streaming
t+00:12  FAULT   inject_router_reboot           -> wifi, mid-flight
t+00:12  wifi    streaming_downlink             refused -- no lease (the fault landed first)
t+00:14  bt      bt_audio_streaming             Connected -> Streaming
t+00:20  matter  complete_matter_commissioning  Commissioning -> Commissioned
t+00:27  FAULT   inject_phone_out_of_range      -> bt, mid-flight
t+00:27  bt      Streaming -> Disconnected      (postcondition: link drops within 15s OK)
  • One fault, two consequences. inject_router_reboot lands while wifi is mid-stream, and the very next wifi call is refused for a reason that only makes sense given the line above it — a reset-per-case suite can never produce that sequence.
  • Three components, one shared clock. Nothing here is scripted in advance. This is one seed, replayed — it produces exactly this sequence every time.

Build a test case from a matrix

One matrix carries everything a chain needs — M[i][j] is the probability of the transition from state i to state j, and the action that causes it rides in the same cell. States plus this one matrix is all a TE has to give; the page draws it exactly the way TC-01's four chains are drawn above. Leave a cell 0 and no edge is drawn.

1 States
2 Matrix — each cell is 0, or p (action)
    • The matrix is the source of truth here, not the chain. MarkovPolicy.matrix() (Slide 03) goes the other way — it derives a matrix from a chain someone already wrote in code, for the maths and for validation. This tool runs that arrow backwards: type the matrix first, get the chain drawn from it.
    • A row that does not sum to 1 is flagged, not silently normalized. validate_chains treats that the same way — a probability row is either right or it is a bug, never something to be quietly rescaled.

    Slide 02

    Architecture Overview

    Configuration feeds the engine loop, the engine loop drives the device, and everything a run produces lands in one folder. The AI never sits inside that loop: it reads the folder once the run has stopped, and what it writes back — the report, and the plan for the next run — is what makes the next run different from this one.

    • One class, however many workers. EngineLoop is instantiated once per worker, not once per component — a walk or probe instance is paced by avgIntervalMs and scoped to one component; a schedule instance reads neither, it just steps through its own list on the clock. What differs between instances is only which kind they are.
    • Concurrent workers rarely contend. dut workers talk to the Pod; equipment workers talk to the plug, the AP, the attenuator. Only the shared state — CompositeState, CoverageTracker — needs a lock.
    • The AI is outside the loop by choice. An LLM picking the next action still picks from the 32 the model already has; reading a finished run, it can say which action is missing. That is why no mode has AI in it.
    • What the AI may write, it writes without asking. An ActionSchedule and the next run plan only ever name actions that already exist. ActionDatabase and MarkovPolicy define what an action means, so they change only through a reviewed proposal — see the proposal flow in docs/data_structure.md for both paths.
    • The counting is Python, never the model. CoverageTracker does set arithmetic, and separates issued from accepted: an action the device refused every time lands in refused_actions, not in the covered count.
    • Swap the driver, not the graph. The same diagram runs against the simulator or a physical bench; nothing above the device boundary changes.

    Slide 03

    Data Structure

    From a TE's matrix to a running call

    A TE only ever writes two things by hand: a matrix — which states, which action moves where, at what probability — and a short list of when a fault should fire. Everything else a call actually needs is looked up by name, out of one shared ActionDatabase, at the moment it's used. TC-01's wifi walk (Slide 01) shows the whole path, end to end.

    TE input MarkovChain Matrix Table

    states: [Disconnected, Connected, Streaming]
matrix:
  [ "0.3 (api_wrong_psk)",       "0.7 (api_connect_wifi)",      "0"                              ]
  [ "0.3 (api_disconnect_wifi)", "0",                           "0.7 (api_streaming_uplink)"     ]
  [ "0.4 (api_disconnect_wifi)", "0",                           "0.6 (api_streaming_downlink)"   ]

    That matrix is nothing but MarkovPolicy.chains["wifi"] unfolded — each row becomes a state key, each non-zero cell becomes one Transition(action, next, p):

    {
  "Disconnected": [{"action": "api_wrong_psk",       "next": "Disconnected", "p": 0.3},
                   {"action": "api_connect_wifi",    "next": "Connected",    "p": 0.7}],
  "Connected":    [{"action": "api_disconnect_wifi", "next": "Disconnected", "p": 0.3},
                   {"action": "api_streaming_uplink","next": "Streaming",    "p": 0.7}],
  "Streaming":    [{"action": "api_disconnect_wifi", "next": "Disconnected", "p": 0.4},
                   {"action": "api_streaming_downlink","next": "Streaming",  "p": 0.6}]
}

    Say the wifi-worker's roll lands on api_connect_wifi. The chain only ever names it — it has no idea what the call checks or does. EngineLoop looks the name up once, into ACTION_DB:

    Action Definition

    ACTION_DB.get("api_connect_wifi")

ActionDefinition(
    name="api_connect_wifi",
    category=Category.API,               # api, not fault_injection
    executor=Executor.DUT,                # the Pod's own API, no bench hardware
    component="wifi",

    guard_text="wifi = Disconnected",
    guard=lambda s: s.wifi is Wifi.DISCONNECTED,

    postcondition_text="wifi = Connected within 30s",
    postcondition=lambda s: s.wifi is Wifi.CONNECTED,

    effect=_connected_wifi,                # below

    postcondition_timeout_ms=30_000,       # unset would default to 10_000
    cleanup_action=None,                   # unset — this action needs no cleanup
)

    A fault takes the same last step from a completely different first one. TE gives it one action name and one time; EngineLoop hits the exact same ACTION_DB.get(name) lookup to find out what it does:

    ActionSchedule Info

    {"workerId": "fault-clock", "actionName": "inject_router_reboot", "scheduledOffsetMs": 12000}

    Three config files, one ACTION_DB.get(name) each: MarkovPolicy names an action for a chain roll, ActionSchedule names one for a clock tick — different deciders, same lookup, and that's everything EngineLoop needs to run either one.

    Slide 04

    Runtime Flow

    Every worker — walk, probe, or schedule — shares one clock, and so does a fourth queue member that isn't a worker at all: the BackgroundMonitor. Session.run() pops whichever one is due next, lets it take exactly one turn, and pushes it back into the queue at whatever time it says it's due again. This is the whole loop:

    • The monitor is not a worker wearing a disguise. It sits in the exact same queue and gets popped the exact same way, but its turn is nothing like a worker's — no ACTION_DB lookup, no guard, no action at all. It just reads the current state, logs it, and reschedules itself at a fixed interval, never a rolled one.
    • Judging is a comparison, not a second lookup. The guard was already checked before execution; judging afterward means comparing that held-or-not flag against what the call actually did — postcondition if the guard held, "refused cleanly" if it didn't. ACTION_DB is only ever consulted once, at Select.
    • A fault worker never waits its turn. Its own next time is just the next entry in its own list, not a reaction to anyone else's state, so it can land back in the queue at a moment that falls in the middle of another worker's action — which is what "mid-flight" means.
    • power = Power_Off and crashed each independently end the session — either is enough, not both together. A device that's off can't do anything else; a device flagged crashed shouldn't be trusted to keep going even if it still looks powered. crashed is a hook for a real bench Driver to set when hardware genuinely hangs — the simulated Driver never sets it, so today this exit is reached only through the clock.

    Slide 05

    What AI Does Here

    Once the engine stops, there's a folder of logs. Reading it takes four steps. In the first two, Python counts and flags. In the last two, the AI reads and proposes. One run carries the example the whole way through: CHAOS-003, TC-01, 24 hours.

    ① Compute — what did the whole run do?

    Python counts every call in the run and sorts the totals by component. No AI is involved, and every number has exactly one right answer.

    componentcallsillegal calls issuedfailedfailure ratepairs reached
    wifi16,971210.01%13 / 39
    bt28,6572,2351,1313.95%13 / 40
    matter8,0462,3791,20314.95%7 / 15
    total53,6754,6162,3354.35%33 / 94

    ② Flag — which numbers are off?

    Python checks the totals against fixed rules and marks what stands out. Each mark comes with the line numbers in the log where that behaviour happened.

    flagwhy it stands outwhere to read
    matter failures14.95% — four times bt's rateEngineEvents:192 · dut:69
    wifi rejection16,971 calls, only 2 of them illegal — wifi's refusals were barely tested—
    matter fdopen files and sockets (file descriptors) up 62% and still climbing at hour 24ResourceSnapshot

    ③ Investigate — why?

    What the AI looks at depends on the kind of flag. A failure leaves lines in a log, so the AI reads those lines. A leak leaves a curve, so the AI looks at a chart.

    Matter failures: read the log. The flag points to this call:

    EngineEvents:192  api_start_matter   matter = Uncommissioned, wifi = Streaming   guard_held: false
EngineEvents:194  oracle: passed false — expected "state unchanged ∧ error returned"
dut.log:69        matter: api_start_matter applied

    The guard requires wifi = Connected. The device started commissioning anyway, so it accepted a call it should have refused. Back in table ①, the same pattern shows up twice: bt accepted 1,131 of its 2,235 illegal calls, and matter accepted 1,203 of its 2,379. Both are about 51%. Two unrelated stacks failing at the same rate looks like one missing check in the device, not two wrong guards in the model. The verdict is a likely device bug, not yet a confirmed one: only a replay that reproduces it confirms it.

    Matter fd: look at the chart.

    • Shape: a leak, not a cache. The fd line climbs at about the same rate from the first hour to the last and never flattens. A cache filling up would level off.
    • Control: it's matter, not the whole system. Four other processes stay inside a narrow band around zero. Matter's growth isn't the device as a whole slowly filling up. bluetoothd memory also rises, more slowly, and has its own flag.
    • Cause: the chart can't separate time from work. Matter was commissioned 116–160 times every hour, all day. Growth that follows the clock and growth that follows the calls draw the same straight line here. That limit is what the next run is designed to resolve.

    ④ Propose — what should the next run do?

    proposalwhat it asks forcomes from
    regressionReplay the matter and bt reproductions; if they reproduce, confirm the device bug③
    targeted_runProbe wifi with illegal calls, so its refusals actually get tested② wifi rejection
    targeted_runLeave matter idle for the first half of the run, then commission it heavily. If the fd slope changes with the calls, the leak is in commissioning.③ matter fd chart

    Every proposal starts as pending. Once a person accepts it, the planner (Slide 08) reads it into the next run. Nothing here changes ActionDatabase or MarkovPolicy.

    Where AI can go further

    • Across releases: compare against the previous firmware to catch slow drifts that no single run shows.
    • Shrink a reproduction: cut a six-step repro down to the fewest steps that still fail.
    • Find model gaps: spot when the device did something the model has no action for, and draft that action.
    • File and follow the bug: check for duplicates, attach the log and the repro, and re-run once a fix lands.

    Slide 06

    Action-Led Test

    TC-01 (Slide 01) is state-led: the worker follows the flow the device was designed for — connect, then get a lease, then stream. Only the transitions somebody drew are ever issued. Every other API in the component is never called at all, in any state. An action-led worker calls them. It ignores the flow and fires whatever the draw hands it at whatever state the device is in, which is how you find out how a state reacts to something it was not expecting: streaming started while nothing is connected, a second disconnect on an already-disconnected link, an address requested before there is a link to have one on.

    TC-01's wifi component, eight hours

    One probe worker, the same component TC-01 walks. The first calls of the run:

    t+  0m  Disconnected  api_inject_wrong_ipaddr   off the flow    ok
t+  3m  Disconnected  inject_ap_psk_changed     off the flow   ok

    • The nine starred cells are the entire state-led run. Everything else on this grid is a call TC-01 cannot produce, no matter how long it runs.
    • All ten gaps are in one column. Streaming is the state the device is hardest to get into, and a probe picking its next call at random does not try to get there — so the cells that stay empty are not the rare actions, they are every action in the rare state.

    Both together — the grid fills

    The gaps close when the two are combined. That is a worker kind of its own — WorkerKind.SWEEP, a fourth alongside walk, probe and schedule. Inside a state it calls only what it has not called there yet; when that list is empty it hands the turn to the chain, which unlike a random draw is guaranteed to pick an action that moves. Off the flow to cover a state, on the flow to leave it.

    WorkerTransitionsState × action
    state-led walk7 / 7 (100%)7 / 39 (21%)

    Same component, same eight hours, same seed. The sweep had all 42 cells just over two hours in, on its 75th call — and across five seeds it landed between 67 and 90 calls every time, against a floor of 42. The probe spent the same eight hours drawing at random and finished at 32.

    Slide 07

    Pure Fuzz Test

    A fuzz test calls the device at random, as hard as it will take, and watches what that does to the device rather than what any one call returned — the questions belong to the hour rather than to the call: does memory climb and stay climbed, does CPU settle back down between bursts, is the thing still answering at the end. This framework runs one without adding anything: a probe already fires without consulting the flow, so four of them with avgIntervalMs on the engine's one-second floor is the entire plan, and BackgroundMonitor — sampling cpu, memory and power every thirty seconds into Log/ResourceSnapshot.json — is already running in every session.

    Simulation numbers

    One hour of configs/fuzz.json, four workers, no code changes:

    calls in 1h      10,558
off the flow      7,570 / 10,558  (72%)
per component    wifi 2,634   bt 2,645   matter 2,650   system 2,629
    • 72% of these calls are pairs no chain declares. A walk cannot issue one — its next call always comes from the chain's row for wherever it is — and no regression suite contains one: api_complete_matter_commissioning against a fabric that was never started, a wrong setup code fed to a commissioning that is not running. Action-led is the kind that reaches them; what fuzz changes is the rate, and that every component is taking them at once.
    • All four components are under pressure at the same time. The load is even to within half a percent, so nothing here is four separate tests sharing a clock — it is one device being pushed on every interface it has, which is the only condition under which a leak in one of them shows up as a slope in the whole.

    Slide 08

    Run Planner

    A test engineer does not configure a run any more. They say what changed, what the bench can drive, and how long it is free — and the planner turns that, plus every previous run folder, into next_run.json. This slide is what that plan is made of: the four kinds of worker, the four things a TE fills in to write one by hand, and the planner itself, deriving a plan live from three answers.

    The four kinds of worker

    Not modes a session picks, but four different answers to one question — what decides the next call. A run usually uses more than one.

    KindWhat chooses the next actionWhat it is for
    walk
    state-led    		The chain: this component's current state has a row, and the row is rolled. The model chooses and judges.Whether the designed flow holds. A realistic walk with a steady state you can state exactly, perturbed on a schedule, measured by how far it drifts and how fast it returns.
    probe
    action-led    		Chance: any action from its pool, at whatever state the device is in.What a state does when called out of order. The chains describe 24 transitions; the device has 84 state × action combinations. A probe is how the rest gets reached.
    sweep
    mix    		What this state has not been called with yet; and when that list empties, the chain, to move somewhere with cells still open.Every cell, in the fewest calls. 84 of 84 in eight hours — against a probe that plateaus short of it and a walk that cannot pass 24.
    schedule
    clock-led    		A list of times: faults, and saved reproductions replayed.Interrupting the other three. A stepwise worker never starts a new action before the last resolves, so only a clock can land a fault mid-flight.
    • No kind terminates by itself. durationMs is what ends the session; a schedule ends when its list runs out, which is why a replay is the one thing whose length you can count in advance.
    • Fuzz is not a fifth kind. It is probe with the pacing on the floor and every component loaded at once (Slide 07) — the guard never gated execution, so there is nothing to switch off. What changes is what gets read afterwards, not what the engine does.
    • Drift belongs to the walk alone. Neither a probe nor a sweep is trying to reproduce realistic usage, so the distribution either one produces means nothing. Reading one number for a mixed session hides that: report drift per component, and only for walked chains.

    Plan a run

    A test engineer picks one of the four, states three things about the bench, and may fine-tune a fifth; everything else is derived. What comes out is a file run.py will accept, block name included. It also lists what the plan gives up, because a plan that names only its wins is advocacy. One difference from pod_mbt/plan.py is worth naming: here a person chooses the test, where that planner works it out from the run folders it has read. A component whose grid is still more than 30% unreached gets swept rather than walked and probed, and once the grid closes it goes back to a walk — the choice this panel puts in a radio button is one the planner makes from evidence.
